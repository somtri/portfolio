# Decisions

Append-only decision ledger. Read in full before proposing any approach in this repo.
Reopening a decision requires naming its ID and new evidence — ideally its revisit condition firing.

## D-001 — Keep the Next.js stack (2026-08-08)
**Decision:** Keep Next.js 16 / React 19 / Tailwind 4 / TypeScript / Vitest / pnpm / Vercel. No framework port for the redesign or the chatbot.
**Rejected:** Astro / SvelteKit port — no measured problem to fix: the site is fully static with three runtime dependencies, and the redesign brief's own prior ("recommend a change only if you can point at a measured problem") found none. The chatbot needs exactly one server route, which Next.js on Vercel provides natively (route handler), so the chatbot imposes no constraint the stack cannot meet.
**Revisit if:** A measured constraint appears — a Core Web Vitals failure attributable to the framework, a build-output regression, or a chatbot requirement (e.g., long-lived connections) that Next.js route handlers cannot serve on Vercel.

## D-003 — RAG-lite retrieval, no vector store, no LangChain (2026-08-08)
**Decision:** The assistant uses build-time section embeddings + in-route cosine top-k + similarity-gated refusal, with automatic full-context fallback when the embedding API fails. No vector database. No LangChain/LangGraph.
**Rejected:** Full-context as the primary path — loses the measurable pre-model refusal gate and exceeds Groq's 12K TPM free cap (~11k tokens/request vs ~2k). Vector database — zero retrieval-quality gain over exact in-process cosine at ~50–80 vectors; adds latency and a dependency. LangChain/LangGraph — no graph in a retrieve→call→validate pipeline; abstracts the parts worth demonstrating; breaks the three-runtime-dependency leanness.
**Revisit if:** Retrieval tests show top-k misses on real questions, or the embedding dependency causes measured latency/reliability problems (either flips v1 to full-context via the shared buildContext seam), or the corpus outgrows single-request context.

## D-016 — Ship an SVG mark with a PNG fallback, no favicon.ico (2026-08-09, revised 2026-08-10)
**Decision:** The site's mark ships through Next's icon/apple-icon conventions plus one runtime-added SVG link. `app/icon.png` (96px) is the declared fallback and `app/apple-icon.png` (180px) serves iOS; `public/icon-dark.svg` and `public/icon-light.svg` carry the themed mark. `app/favicon.ico` is deleted; `/favicon.ico` 404s by design. The mark itself is a traced path, not text: Hack Bold's ">" read out of the rendered glyph mask row by row (scratchpad `brand/measure.js`), so no icon file needs a webfont.
**Rejected:** A hand-built ICO — Next's decoder requires an RGBA PNG payload and Playwright strips the alpha channel when the image is fully opaque, so the build fails. Keeping Next's scaffold favicon — it is the Vercel logo, which is what the owner asked to remove. Shipping the SVG alone — Safari ignores SVG favicons entirely (checked 2026-08-10), so Safari would show no mark. Drawing the chevron by hand — the traced path measures 95.4% mask overlap with the real glyph, and the gap is a known 0.25px recentre rather than a guess.
**Revisit if:** Safari ships SVG favicon support (then `icon.png` is dead weight), or a surface is found that requests `/favicon.ico` directly — then put a real ICO in `public/`, where files are served as-is and never touched by Next's decoder.

**Decision:** `components/TabIcon.tsx` creates one `<link rel="icon" type="image/svg+xml">` in an effect and points it at `/icon-dark.svg` or `/icon-light.svg` from `document.documentElement.dataset.theme`, re-syncing on the existing `portfolio-theme-change` event. A static single mark — the owner asked for the icon to follow the theme.
**Evidence:** On the production build the head declares `/icon.png sizes="96x96"` plus this link with no size, and headed Chrome requests `/icon-dark.svg` on load, `/icon-light.svg` on toggling light, and back again. 0/6 hydration warnings; no console errors. ## D-019 — The tab icon ships two themed formats, both links owned by TabIcon (2026-08-10)
**Supersedes** the icon file-set cell of D-016 and the single-link cell of D-017. Everything else in both entries stands, including the traced-path mark and the site-toggle behaviour.
**Decision:** `public/icon-dark.svg`, `public/icon-light.svg`, `public/icon-dark.png` and `public/icon-light.png` carry the mark in both themes. `components/TabIcon.tsx` creates BOTH icon links itself — the PNG with `sizes="96x96"`, the SVG with none — and re-points both on the theme toggle. Next's `app/icon.png` file convention is deleted. `public/favicon.ico` ships but is deliberately never declared as a `<link>`. `app/apple-icon.png` is unchanged.
**Why two formats:** Safari ignores SVG favicons entirely, so without a themed PNG Safari could not follow the theme at all — the owner asked for it to.
**Why TabIcon owns both:** a file-convention icon is rendered by React; rewriting its href either races hydration (D-014) or is reset by React's head updates on navigation. Elements created in the effect are ours alone.
**Why favicon.ico is undeclared:** declared, it would compete in the browser's icon selection against the themed pair. Undeclared, it answers only the implicit `/favicon.ico` request, which is exactly the two cases the JS-created links cannot cover — JavaScript disabled, and the window before hydration. It lives in `public/` because Next's own ICO decoder rejects a non-RGBA PNG payload while `public/` is served as-is. This is the fallback D-016's revisit condition anticipated.
**Rejected:** Keeping `app/icon.png` declared alongside — two PNG icon links with no reliable rule for which the browser prefers. Removing React's link from the DOM instead — mutating a React-owned node, the same class of bug as D-014.
**Evidence:** headed Chrome on the production build requests `/icon-dark.svg` on load, `/icon-light.svg` on toggling light, and back; 0/6 hydration warnings; no console errors; all five icon assets serve 200.
**Known limit:** the Safari path is UNVERIFIED. There is no Safari on the development machine, so it has never been watched working.
**Revisit if:** Safari ships SVG favicon support, in which case both PNGs become dead weight.

## D-020 — Embeddings are committed, and guarded by a corpus hash (2026-08-10)
**Decision:** `lib/assistant/vectors.json` is committed, not generated at deploy time. `pnpm embed` also writes `lib/assistant/vectors.meta.json` holding a sha256 of the corpus, and `tests/assistant/vectors.test.ts` compares it against the live corpus. Both tests skip while no embeddings are committed. `pnpm embed` runs through `node --env-file-if-exists=.env.local --import tsx`.
**The bug this fixes:** `.gitignore` ignored `vectors.json` while `lib/assistant/vectors.ts` reads it from disk at request time. Deployed, retrieval would have silently fallen back to full-context — no error, no signal, just worse answers. A probe confirmed Next's file tracing does bundle the file into the `/api/ask` lambda once it exists at build time, so the gitignore was the only thing in the way.
**Rejected:** Running `pnpm embed` during the Vercel build — always fresh, but it makes the build depend on Cloudflare and on secrets, breaking the standing guarantee that lint, typecheck, test and build all pass offline with no env vars. Committing the vectors with no guard — derived data drifts from `data/*.ts` silently, which is the same failure mode in slower motion. Adding a dotenv dependency — Node's own `--env-file-if-exists` does the job with no new package, and the repo's zero-runtime-dependency rule makes any new dependency expensive.
**Revisit if:** the corpus grows large enough that committing the vectors bloats the repo, or content starts changing often enough that a manual re-embed becomes the bottleneck.

## D-021 — Assistant guardrails are layered, and checked on both sides (2026-08-10)
**Decision:** The `/api/ask` posture is four ordered layers, not one gate. Before the provider call: input sanitization (invisible characters stripped, `<visitor-question>` tags removed so a question cannot close its own block), a narrow injection screen, and a relevance gate — cosine similarity when embeddings exist, lexical corpus overlap when they do not. At the provider call: the question travels inside `<visitor-question>` tags and the system prompt states in rule 4 that everything inside them is a question, never an instruction. After the call: a prompt-fingerprint check and the existing citation validator. Every layer returns the same refusal body, so probing reveals which questions are answered, never which rule stopped one. `tests/assistant/secrets.test.ts` locks key handling — no `NEXT_PUBLIC_` assistant variable, no provider variable in a client component, no key-shaped literal in source, `.env.example` names-only, `.gitignore` un-ignoring nothing but the example.
**The hole this closes:** the full-context fallback had no refusal gate at all. `buildContext` sends the whole corpus when there are no embeddings to rank against, and in that mode there is no similarity score to refuse on — so every question, on any subject, reached the model with the entire corpus attached. Since no embeddings have ever been committed, that was the only mode the assistant had.
**Rejected:** Refusing outright in full-context mode — it would delete the automatic fallback D-003 designed on purpose, turning an embedding-provider outage into a dead assistant. Prompt rules alone — a prompt rule is a request to the model, not a control, which is why rules 5 and 6 are also checked on the output. An output-only defence — it pays for a provider call on every attack, and Groq's free tier is 1,000 requests a day. A broad keyword filter — `debug mode` and `god mode` are things a visitor might genuinely ask about the RPG project, so each pattern pairs an imperative with a specific target, and six ordinary questions are pinned in the tests as the cost boundary.
**Known limit:** the prompt-fingerprint check has never fired against a real model, only a synthetic answer. Whether a coerced model reproduces those sentences verbatim is unverified until keys are live.
**Revisit if:** a real question is reported as refused (loosen the pattern that caught it — each is a one-line revert), or a live transcript shows an attack shape none of the four layers catches.

## D-022 — Work lands through issues, pull requests and CI (2026-08-10)
**Decision:** Changes reach `main` through a pull request with green CI, never a direct push. `.github/workflows/ci.yml` runs lint, typecheck, test and build on every pull request with no secrets set, which keeps the offline-build guarantee honest. Tracked work opens as an issue first and the pull request closes it by number. Related work stacks: a branch off a feature branch, merged into it, rather than one unreviewable pull request. Commits stay atomic and single-concern, and the project builds at every commit.
**Rejected:** Committing to `main` — it auto-deploys to production, so every push would be an unreviewed deploy (D-002 already ruled this out; this entry adds the mechanism). One pull request carrying every change — the redesign branch is 40 commits and 98 files, past any useful review size; stacking is what makes the parts reviewable. Running the checks only locally — a green local run says nothing about a clean checkout, and `--frozen-lockfile` in CI is what catches a lockfile that drifted. Setting provider secrets in CI — the build must pass with no environment variables, and a CI job that has keys stops proving that.
**Revisit if:** the repository gains a second contributor (then branch protection and required reviews replace convention), or CI minutes become a real cost.

## D-023 — Answers cite the full section id; the validator normalizes to the page (2026-08-11)
**Decision:** `buildSystemPrompt` serializes each section under its full id, fragment included (`projects/runscope#overview`), and rule 2 tells the model to cite exactly what the heading shows. `extractCitations` accepts `page` or `page#fragment` and normalizes to the page cite before checking it against the known set. The response's `citations` array therefore always carries page-level cites with real hrefs.
**The bug this fixes:** the citation pattern had no `#` while 50 of the 59 sections carry one. The model cited correctly, `extractCitations` returned nothing, `validateAnswer` reported `no-citations`, and the handler replaced a good answer with the refusal. Only `profile/main` and the eight `skills/*` sections — the ones with no fragment — could ever be answered. It shipped to production and was found by probing the live endpoint, not by a test.
**Rejected:** Serializing sections under their `cite` instead of their `id` — several sections share one cite, so the model would see repeated identical headings and lose the ability to point at the specific passage it used. Dropping fragments from the ids in `buildCorpus` — the fragment is what makes a section addressable, and the ids feed the embeddings too. Loosening `validateAnswer` to accept an uncited answer — that deletes the grounding guarantee D-003 exists for.
**Why no test caught it:** every assistant fixture used hand-written ids, and every one happened to carry no fragment, so the fixtures could not produce the failing shape. The regression test now builds from the real corpus and asserts all 59 sections are citable by their full id; reverting the pattern fails 5 tests.
**Revisit if:** the corpus stops using fragment ids, or citation display needs passage-level granularity rather than page-level.

## D-024 — TypeScript stays below 6.1 and ESLint below 10 (2026-08-11)
**Decision:** `typescript` is pinned to `^5.9.3` and `eslint` to `^9.39.1`, and both majors are ignored in `.github/dependabot.yml`. `next` and `eslint-config-next` are grouped so they move in lockstep, and the grouped dev-dependency PR is restricted to minor and patch so every major arrives on its own.
**Why:** both ceilings are upstream, in the newest published versions, and both surface through `eslint-config-next`. `typescript-eslint@8.67.0` declares `typescript: >=4.8.4 <6.1.0` and throws outright on TS 7. `eslint-plugin-react@7.37.5` declares `eslint: ^3 || ... || ^9.7` and calls a context API ESLint 10 removed; `eslint-config-next` depends on `eslint-plugin-react: ^7.37.0`, so ESLint 10 cannot lint a Next project at all.
**Rejected:** Upgrading the linters instead — no released version of either supports the newer major, checked at the registry rather than assumed. Dropping the lint gate to allow the newer majors — lint is one of the four checks the project's definition of done rests on. Leaving the majors un-ignored so they arrive and fail — true to the evidence, but it produces a red pull request every week that someone has to close, and a habit of closing red PRs is what caused the outage.
**How this was learned:** the grouped dev-dependency bump carried both majors behind five safe ones, broke lint and the build, and was merged while its checks were already red. `main` was red until it was reverted.
**Revisit if:** `typescript-eslint` widens its peer range past 6.1, or any `eslint-plugin-react` release supports ESLint 10. Each ignore entry names its own blocker so the condition is checkable in one lookup.
