Keep tests\ green — they guard honest-results wording (SmartSignal simulation caveat, Cine ML post-release framing, MacroMarkets negative result).

- Assistant (lib\assistant\): RAG-lite per D-003 — no vector DB, no LangChain. Providers per D-004: Groq chat + Cloudflare embeddings via env-configured OpenAI-compatible fetch adapters; NVIDIA is dev/eval only (its trial ToS bars free production use). Never let a key reach the browser; .env.example holds names only, and tests\assistant\secrets.test.ts enforces that.
- Assistant guardrails (D-021, lib\assistant\guardrails.ts): four ordered layers — sanitize and screen the question, gate on relevance (cosine when embeddings exist, lexical corpus overlap when they do not), deliver the question inside `<visitor-question>` tags that the system prompt names as data, then check the answer for prompt leakage and valid citations. Every layer returns the SAME refusal body on purpose. The injection screen is deliberately narrow — six ordinary questions are pinned in tests as its cost boundary; if a real question gets refused, loosen the one regex that caught it. Verify any change to this file against a running production build, not just unit tests.
- Assistant citations (D-023): sections are serialized to the model under their FULL id, fragment included (projects/runscope#overview), and extractCitations normalizes `page#fragment` to the page cite before validating. 50 of 59 ids carry a fragment, so a citation pattern without `#` silently turns every good answer into the refusal — that shipped to production once. Assistant test fixtures must use fragment ids, or they cannot reproduce the failing shape.
- Diagnosing /api/ask: every guardrail returns the SAME refusal body on purpose, so a production response never says which check fired. Reproduce locally — .env.local holds real keys — with a throwaway script that prints the raw model answer and each validator verdict, then delete it. Do not exercise Groq locally while probing production: they share the account and the 12k-tokens-per-minute ceiling, and the resulting 503 looks like a production fault.
- Dependencies (D-024): typescript is pinned `^5.9.3` and eslint `^9.39.1`, both blocked upstream through eslint-config-next — typescript-eslint peers `<6.1.0`, eslint-plugin-react peers to `^9.7`. Both majors are ignored in .github/dependabot.yml. next and eslint-config-next move in lockstep, and the `next` group MUST stay above the dev group because a dependency joins the first group it matches.
- Verification bar: pnpm lint, typecheck, test, build — all green before claiming done. All four pass offline with no env vars (fallback paths guarantee it), and CI re-runs them on every PR with no secrets set, which is what keeps that guarantee honest. CI is advisory: nothing blocks merging a red PR, which is how main went down once.
- Git (D-022): work opens as a GitHub issue, lands on a branch, and merges through a PR with green CI — never a direct push to main. Stack related work as a branch off a feature branch rather than growing one unreviewable PR. Never push or deploy without the owner's say-so; main auto-deploys to production. Never use Vercel CLI to deploy.
